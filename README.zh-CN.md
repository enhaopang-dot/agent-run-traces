## 一句话说清

**没有痕迹，所有优化都是感觉。**

这套方法给 Agent 补一条最小闭环：模型调用留全轨迹，运行结果留迟到分数。
跑起来之后，你能回答一个此前答不上的问题——**这次改完，到底有没有变好。**

## 三条设计

### 观测点只放一个

所有模型调用收敛到一个封装函数，轨迹只在这一层记。

散在各 Agent 内部的埋点会随框架版本烂掉，还会漏掉通过其他路径发出的调用。
放在唯一出入口，改一次全局生效。

### 每次运行带 run_id

一次运行 = 一个 `run_id`，把这一轮的所有调用串起来。

没有 run_id 的轨迹等于没记——你没法把「调了三次模型」和「结论对不对」关联起来。

### 回标用人的动作

分数不靠模型自评，靠你已经在做的事：

| 动作 | 分数 |
|---|---|
| 采纳 | 对 |
| 跳过 | 错 |
| 改了再做 | 方向对、执行不到位 |

事后回填，不必实时。让模型给自己打分不可靠，让人的行为当分数既准又免费。

## 为什么是「延迟」回标

建议刚生成时，没人知道它对不对。
三天后做没做、做完有没有效果，才是真信号。

生成时记 run_id，过几天回填结果，允许「待定」，不允许不记。

## 比自评更靠谱的：横向比较

同一个任务让模型跑两次，互相比。

两条轨迹放一起，谁更好一眼能看出来——比让它给自己打 8 分还是 9 分可靠得多。

## 最小落地

| 文件 | 内容 |
|---|---|
| `llm_trace.jsonl` | 每次调用一行：run_id、模型、输入输出摘要、耗时、token |
| 运行记录 | 每次运行：run_id、结论、置信度 |
| 回标字段 | 每条结论：采纳/跳过/改了再做/待定 + 回填时间 |

三个文件，就能回答三个问题：调了几次、花了多少、后来对没对。

## 不需要什么

不需要训练模型、不需要 token 级 logprob、不需要 K8s 编排。

单机一个 JSONL 就能起步。先把闭环跑通，再谈规模化。
